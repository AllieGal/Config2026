### A) Summary

Craig Lebenz (Developer Relations, Google Flutter team) introduces Generative UI (GenUI) — a paradigm in which AI agents generate user interfaces dynamically at runtime rather than serving static, deterministic UI code. Using two Google demo apps (Gen Latte, a coffee-ordering experience, and Hatcha, a party planning app), he proposes a four-tier adoption spectrum from fully deterministic (Level 0) to full AI delegation of both UI composition and application state (Level 3). The central argument is that GenUI is not a binary feature — it is a dial on a spectrum — and as it becomes more prevalent, it creates a new category of design and engineering collaboration problems: unknown content length, dynamic component selection, consistency vs. creativity trade-offs, and caching of AI-generated responses. An open protocol (A2UI) is available today.

---

### B) Key points and tools

- **GenUI (Generative UI)**: AI agents generate rich UI at runtime, not just text; non-deterministic UI output
- **A2UI protocol** (agent-to-user-interface): open spec for how agents generate and communicate UI; available at a2ui.org
- **Four-tier GenUI spectrum:**
  1. **Level 0 — One-sided UI**: fully deterministic; all logic client or server; covers the vast majority of apps today including early ChatGPT/Gemini web UIs
  2. **Level 1 — Full-stack UI**: server + client responsibilities split; still deterministic; most news sites, A/B testing frameworks
  3. **Level 2 — AI-driven server-driven UI**: AI decides what to show at runtime; non-deterministic begins here; Gen Latte example (questions generated by Gemini at runtime)
  4. **Level 3 — Full AI delegation**: AI owns both UI composition AND application state; button presses routed to AI, not local code; Hatcha party planning app example
- Level 2 design challenges: unknown text length, unknown number of options, responsive layout for AI-generated content, text overflow in headings
- Level 3 design challenges: information hierarchy consistency, UX consistency, coarse vs. fine-grained widget catalog trade-off
- **Coarse-grained widget catalog**: high-level intelligent components; more UX consistent, less creatively flexible
- **Fine-grained widget catalog**: design system primitives (buttons, text, containers); AI composes freely; more creative, less consistent
- **Level 3 personalization opportunity**: observe user journey patterns → compose custom screens on the fly → cache AI-generated output for repeat users (saves token cost)
- Current barriers: token cost, LLM latency; mitigated over time as on-device models improve
- **Gemini 4** (Google on-device model): already capable on powerful laptops; phones expected within a few years
- **Flutter**: Google's multi-platform UI toolkit; **Nano Banana**: Google's image generation model

### C) Verified takeaways (with quotes)

**1. As GenUI grows, APIs need to support more dynamic, runtime-determined data needs.**
> "Here's our design system, here's our grid rules, and here's the user and what we think they're trying to do — go crazy."

`[ANALOGOUS]` APIs that return fixed response schemas will face pressure as AI-driven clients become more common (both internal and customer-facing); those clients will increasingly need composable, flexible data rather than fixed objects. This is a forward-looking API design consideration for new service work.

**2. The coarse vs. fine-grained component catalog trade-off maps directly to API design decisions.**
> "Coarse-grained... affords users more UX consistency, more predictability, but at the cost of unbounded creativity."

`[ANALOGOUS]` When building REST APIs for AI-driven consumers: coarse-grained endpoints (rich, flexible, self-describing responses) vs. fine-grained composable endpoints present the same trade-off. This choice should be deliberate when designing APIs that AI agents will consume.

**3. Caching AI-generated responses is a cost management and performance pattern.**
> "You could actually cache that output of the A2UI protocol and save on the token cost the next time that user shows up."

Directly applicable if the team builds AI-generated response features in internal tools or eCommerce services — cache stable AI outputs aggressively rather than re-generating on every request.

**4. Non-deterministic outputs break traditional testing assumptions.**
`[no direct quote available]`

`[ANALOGOUS]` If the team's internal apps or APIs adopt GenUI or AI-generated response patterns, traditional end-to-end tests that assert specific UI output will fail. Testing strategies need to shift from "assert exact output" to "assert behavioral constraints." This is a CI/CD consideration.

### D) Role and team actions (including AI enhancements)

1. **Track the A2UI protocol (a2ui.org).** If eCommerce discovery experiences move toward GenUI (AI-assembled product grids, dynamic filters), the team's catalog and inventory APIs will need to support dynamic data composition at runtime.

2. **Deliberately choose coarse vs. fine-grained granularity when designing new APIs for AI-driven consumers.** Document the trade-off in API design records — coarse serves AI clients that need to reason about data; fine-grained gives AI more compositional flexibility. `[INFERRED]`

3. **Establish a caching strategy for any AI-generated responses the team adds to services.** Token costs and LLM latency are real today; cache stable or repeat-pattern outputs aggressively. `[INFERRED]`

4. **Plan for non-deterministic test strategies.** As the team adds AI-generated features, update CI/CD pipelines to test behavioral constraints rather than exact outputs. `[INFERRED]`

### F) Key terms reference

| Term | Definition |
| --- | --- |
| GenUI (Generative UI) | AI agents that generate user interface elements dynamically at runtime, rather than serving deterministic UI code |
| A2UI | Agent-to-user-interface protocol; open spec for how AI agents communicate UI directives to clients |
| Level 0–3 GenUI tiers | Spectrum from fully deterministic UI (Level 0) to full AI delegation of UI composition and application state (Level 3) |
| Deterministic UI | UI where code always produces the same output given the same input; covers the vast majority of apps today |
| Non-deterministic UI | UI where an AI agent determines what to show at runtime; output varies with context |
| Coarse-grained widget catalog | High-level, intelligent UI components handed to the AI; more consistent, less flexible |
| Fine-grained widget catalog | Design system primitives (buttons, text, containers) handed to AI; more creatively flexible, less consistent |
| One-sided UI | Level 0: all UI logic resides entirely on either the client or the server |
| Server-driven UI | UI where the server determines what to render; the AI variant of this is Level 2 GenUI |
